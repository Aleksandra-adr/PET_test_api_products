# Чек-лист тестов — product-showcase API

Исправленный и сокращённый вариант. Общее правило: везде, где ожидается ошибка,
проверяем `response.json()["code"]` из фиксированного набора
(`VALIDATION_ERROR`, `MISSING_FIELD`, `UNKNOWN_FIELD`, `UNAUTHORIZED`,
`INVALID_CREDENTIALS`, `NOT_FOUND`), а не точный текст `message` — он не
гарантирован контрактом.

Пункты, отмеченные **(параметризовать)**, — это один тестовый файл с одной
функцией и `@pytest.mark.parametrize`, а не отдельная функция на каждый пункт.

---

## POST /auth/login

**Позитивные**
- [ ] Успешный логин `admin` / `admin123` → 200, есть `access_token`, `token_type == "bearer"`
- [ ] Токен из логина реально работает на защищённом эндпоинте (`POST /products`) → 200/201

**Негативные — неверные credentials → 401 `INVALID_CREDENTIALS`** (параметризовать)
- [ ] Неверный пароль (`admin` / `wrong`)
- [ ] Несуществующий пользователь
- [ ] Пустой `username` (`""`)
- [ ] Пустой `password` (`""`)
- [ ] Числовые/произвольные строки в обоих полях

**Негативные — поле отсутствует в теле → 400 `MISSING_FIELD`** (параметризовать)
- [ ] Нет ключа `username`
- [ ] Нет ключа `password`
- [ ] Пустое тело `{}`

**Негативные — прочее**
- [ ] Невалидный JSON (битый синтаксис) → 400 `VALIDATION_ERROR`

**Отложено (нужна спец. подготовка)**
- [ ] Истёкший токен — требует укороченного TTL в тестовом окружении, вернуться к этому позже

## GET /products (список)

**Пагинация — позитив** (параметризовать: `limit`, `offset` → ожидаемая длина/срез)
- [ ] Без параметров → default `limit=20, offset=0`
- [ ] `limit=10` → 10 элементов
- [ ] `offset=5` → пропущены первые 5
- [ ] `limit=1` (минимум)
- [ ] `limit=100` (максимум)
- [ ] `limit=10&offset=20` → элементы 21–30

**Фильтр по цене — позитив** (параметризовать: `min_price`, `max_price` → ожидаемый набор)
- [ ] только `min_price`
- [ ] только `max_price`
- [ ] диапазон `min_price` + `max_price`
- [ ] `min_price == max_price`
- [ ] `min_price=0`

**Сортировка — позитив** (параметризовать все 4 значения)
- [ ] `price_asc`, `price_desc`, `name_asc`, `name_desc`

**Граничные / комбинированные — позитив**
- [ ] фильтр + сортировка + пагинация вместе → порядок: сначала фильтр, потом сортировка, потом пагинация
- [ ] фильтр не находит ничего (`min_price=10000`) → 200, пустой массив
- [ ] `offset` больше количества товаров → 200, пустой массив

**Негативные — невалидные query-параметры → 400 `VALIDATION_ERROR`** (параметризовать)
- [ ] `limit=0`
- [ ] `limit=-5`
- [ ] `limit=101`
- [ ] `limit=abc`
- [ ] `limit=10.5`
- [ ] `offset=-1`
- [ ] `offset=abc`
- [ ] `min_price=abc`
- [ ] `max_price=abc`
- [ ] `sort=invalid_value`
- [ ] `sort=PRICE_ASC` (регистр важен, значение должно быть точным)

> Убрано (в API такой валидации нет — реальное поведение 200, не 400):
> `min_price > max_price`, отрицательные `min_price`/`max_price`,
> `min_price=null`/`max_price=null`/`sort=null` как «фильтр игнорируется»
> (на деле строка `"null"` не проходит валидацию типа → 400, попадает в блок выше).

## GET /products/{id}

**Позитивные**
- [ ] Создать товар → получить его по id → 200, все поля совпадают
- [ ] Структура и типы ответа: `id` (str/uuid), `name` (str), `price` (number), `description` (str или null)

**Негативные**
- [ ] Несуществующий id (любая строка, не совпадающая ни с одним товаром) → 404 `NOT_FOUND`

> Убрано: авторизация не проверяется — эндпоинт публичный (`Depends` на auth
> отсутствует в коде). Убрано «невалидный формат id» — id это просто строка
> без валидации формата, любой несовпадающий id даёт 404, а не 400.

---

## POST /products (требует авторизации)

**Позитивные**
- [ ] Только обязательные поля (`name`, `price`) → 201
- [ ] Все поля, включая `description` → 201
- [ ] `description` отсутствует в теле → 201, `description == null`
- [ ] `description: null` явно → 201
- [ ] Дробная цена (`299.99`) → 201

**Негативные — отсутствует обязательное поле → 400 `MISSING_FIELD`** (параметризовать)
- [ ] нет `name`
- [ ] нет `price`

**Негативные — валидация значения → 400 `VALIDATION_ERROR`** (параметризовать)
- [ ] `name = ""` (пусто/только пробелы)
- [ ] `price = 0`
- [ ] `price` отрицательная
- [ ] `price` — строка (`"abc"`)
- [ ] `name` — число

**Негативные — прочее**
- [ ] Неизвестное поле в теле → 400 `UNKNOWN_FIELD`
- [ ] Без заголовка `Authorization` → 401 `UNAUTHORIZED`
- [ ] С мусорным токеном → 401 `UNAUTHORIZED`
- [ ] Невалидный JSON → 400 `VALIDATION_ERROR`

**Доп. проверка**
- [ ] Созданный товар действительно виден через `GET /products/{id}`

## PUT /products/{id} (требует авторизации, полная замена)

**Позитивные**
- [ ] Обновление всех полей → 200, новые значения применились
- [ ] `description: null` → 200
- [ ] Повторная отправка того же тела (идемпотентность) → 200 оба раза, одинаковый результат
- [ ] После PUT — `GET` показывает именно новые данные, старые не сохранились

**Негативные — отсутствует обязательное поле → 400 `MISSING_FIELD`** (параметризовать)
- [ ] нет `name`
- [ ] нет `price`
- [ ] нет ключа `description` (в отличие от POST — здесь он обязателен, хоть и может быть `null`)

**Негативные — валидация значения → 400 `VALIDATION_ERROR`** (параметризовать)
- [ ] `name = ""`
- [ ] `price = 0` или отрицательная
- [ ] `price` — строка

**Негативные — прочее**
- [ ] Неизвестное поле → 400 `UNKNOWN_FIELD`
- [ ] Обновление несуществующего id → 404 `NOT_FOUND`
- [ ] Без `Authorization` → 401 `UNAUTHORIZED`
- [ ] С мусорным токеном → 401 `UNAUTHORIZED`

> Убрано: «невалидный id (строка) → 400» — это тот же случай, что и
> «несуществующий id» выше, реальный результат 404.

---

## DELETE /products/{id} (требует авторизации)

**Позитивные**
- [ ] Удаление существующего товара → 204, пустое тело
- [ ] После удаления `GET /products/{id}` → 404
- [ ] Повторное удаление того же id (идемпотентность) → первый раз 204, второй раз 404

**Негативные**
- [ ] Несуществующий id → 404 `NOT_FOUND`
- [ ] Без `Authorization` → 401 `UNAUTHORIZED`
- [ ] С мусорным токеном → 401 `UNAUTHORIZED`

> Убрано: «невалидный id (строка/отрицательный/0) → 400» — по факту всё
> сводится к «несуществующий id → 404», отдельный кейс не нужен.
