# Чек-лист тестов — product-showcase API

Исправленный и сокращённый вариант. Общее правило: везде, где ожидается ошибка,
проверяем `response.json()["code"]` из фиксированного набора
(`VALIDATION_ERROR`, `MISSING_FIELD`, `UNKNOWN_FIELD`, `UNAUTHORIZED`,
`INVALID_CREDENTIALS`, `NOT_FOUND`), а не точный текст `message` — он не
гарантирован контрактом.

Пункты, отмеченные **(параметризовать)**, — это один тестовый файл с одной
функцией и `@pytest.mark.parametrize`, а не отдельная функция на каждый пункт.
Несколько TC-id под одним заголовком "(параметризовать)" означают, что все они
покрываются одной параметризованной тестовой функцией — это нормально,
не нужно по функции на TC.

## GET /products (список)

**Пагинация — позитив** (параметризовать: `limit`, `offset` → ожидаемая длина/срез)
- [x] **TC-LIST-01** Без параметров → default `limit=20, offset=0`
- [ ] **TC-LIST-02** `limit=10` → 10 элементов
- [ ] **TC-LIST-03** `offset=5` → пропущены первые 5
- [ ] **TC-LIST-04** `limit=1` (минимум)
- [ ] **TC-LIST-05** `limit=100` (максимум)
- [ ] **TC-LIST-06** `limit=10&offset=20` → элементы 21–30

**Фильтр по цене — позитив** (параметризовать: `min_price`, `max_price` → ожидаемый набор)
- [ ] **TC-LIST-07** только `min_price`
- [ ] **TC-LIST-08** только `max_price`
- [ ] **TC-LIST-09** диапазон `min_price` + `max_price`
- [ ] **TC-LIST-10** `min_price == max_price`
- [ ] **TC-LIST-11** `min_price=0`

**Сортировка — позитив** (параметризовать все 4 значения)
- [ ] **TC-LIST-12** `sort=price_asc` ← сейчас работаем здесь
- [ ] **TC-LIST-13** `sort=price_desc`
- [ ] **TC-LIST-14** `sort=name_asc`
- [ ] **TC-LIST-15** `sort=name_desc`

**Граничные / комбинированные — позитив**
- [ ] **TC-LIST-16** фильтр + сортировка + пагинация вместе → порядок: сначала фильтр, потом сортировка, потом пагинация
- [ ] **TC-LIST-17** фильтр не находит ничего (`min_price=10000`) → 200, пустой массив
- [ ] **TC-LIST-18** `offset` больше количества товаров → 200, пустой массив

**Негативные — невалидные query-параметры → 400 `VALIDATION_ERROR`** (параметризовать)
- [ ] **TC-LIST-19** `limit=0`
- [ ] **TC-LIST-20** `limit=-5`
- [ ] **TC-LIST-21** `limit=101`
- [ ] **TC-LIST-22** `limit=abc`
- [ ] **TC-LIST-23** `limit=10.5`
- [ ] **TC-LIST-24** `offset=-1`
- [ ] **TC-LIST-25** `offset=abc`
- [ ] **TC-LIST-26** `min_price=abc`
- [ ] **TC-LIST-27** `max_price=abc`
- [ ] **TC-LIST-28** `sort=invalid_value`
- [ ] **TC-LIST-29** `sort=PRICE_ASC` (регистр важен, значение должно быть точным)

> Убрано (в API такой валидации нет — реальное поведение 200, не 400):
> `min_price > max_price`, отрицательные `min_price`/`max_price`,
> `min_price=null`/`max_price=null`/`sort=null` как «фильтр игнорируется»
> (на деле строка `"null"` не проходит валидацию типа → 400, попадает в блок выше).

## GET /products/{id}

**Позитивные**
- [ ] **TC-ITEM-01** Создать товар → получить его по id → 200, все поля совпадают
- [ ] **TC-ITEM-02** Структура и типы ответа: `id` (str/uuid), `name` (str), `price` (number), `description` (str или null)

**Негативные**
- [ ] **TC-ITEM-03** Несуществующий id (любая строка, не совпадающая ни с одним товаром) → 404 `NOT_FOUND`

> Убрано: авторизация не проверяется — эндпоинт публичный (`Depends` на auth
> отсутствует в коде). Убрано «невалидный формат id» — id это просто строка
> без валидации формата, любой несовпадающий id даёт 404, а не 400.

**Негативные — прочее**
- [ ] **TC-UPDATE-11** Неизвестное поле → 400 `UNKNOWN_FIELD`
